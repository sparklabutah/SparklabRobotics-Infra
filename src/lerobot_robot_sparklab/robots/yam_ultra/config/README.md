# config

Rig identity for *this physical YAM-Ultra* — the serial numbers, presets and
measurements that would be wrong on any other rig, even another YAM-Ultra.

```
cameras.yaml              which cameras exist, their ids and capture settings
hand_default.json         RealSense advanced-mode preset for the D405 wrists
thirdperson_default.json  RealSense advanced-mode preset for the D435 top cam
intrinsics.yaml           exported intrinsics for all three cameras
```

Generic RealSense *tooling* lives in [`cameras/`](../../../cameras/README.md).
Only rig-specific values belong here.

## `cameras.yaml` is read by two processes

Both `relay/server.py` (the live VR view) and `follower.py` (dataset
recording) read this one file. Keep it that way — two sources of camera truth
is how a dataset ends up recorded from a differently-configured camera than
the operator was watching.

| id | serial | model | capture | dataset |
|---|---|---|---|---|
| `left_wrist` | 353322271147 | D405 | 640×480 | crop → 640×360 |
| `right_wrist` | 323622272781 | D405 | 640×480 | crop → 640×360 |
| `top` | 243322071190 | D435 | 640×360 | native |

**Ids are load-bearing in three places at once**: the relay's VR panel slots,
the LeRobot dataset keys (`observation.images.<id>`), and the follower's
camera dict. Renaming one renames a dataset column.

## Why 360, and why crop rather than resize

640×360 matches the `allenai/MolmoAct2-BimanualYAM-Dataset` schema, so a
MolmoAct2 checkpoint's preprocessing sees the frame shape it was trained on.

`height` is what's actually requested from the sensor and must be a profile
the camera really offers. The D435 supports 360 natively and captures there
directly. The **D405 wrist cameras have no 360-tall mode at all** — at 640
wide, only 480 is offered, confirmed by reading
`rs.sensor.get_stream_profiles()` rather than assumed. So they capture at 480
and `crop_height: 360` center-crops 60 px off top and bottom in software.

Cropping, not stretch-resizing, because a resize distorts proportions relative
to the training frames — a subtle, systematic mismatch that a policy will
happily learn around and then fail on.

## Presets

`advanced_json` points at a preset exported from `realsense-viewer`'s "Save
settings to file", locking exposure, white balance and color correction.

**Not applied automatically.** Run once per power-up, before the relay or
`lerobot-record`:

```bash
python -m lerobot_robot_sparklab.cameras.apply_camera_presets
```

It sticks in the device's own memory until power is lost, so later runs just
see an already-locked camera.

There is also a lighter inline path — `exposure` / `white_balance` / `gain`
keys applied by the relay's reader on every connect. Currently unused here.
**Don't set both for one camera.**

## `intrinsics.yaml`

Generated by `cameras.export_intrinsics`, covering depth and color streams per
camera. Needed for 3D reasoning from these frames; irrelevant to policies that
consume raw pixels, which is currently all of them.

## Replacing a camera

Serials are physical identity — swap a camera and you must update
`cameras.yaml`, re-apply presets, and re-export intrinsics. Nothing detects a
swapped serial for you; the symptom is a camera that fails to open, or worse,
a rig where left and right wrists are silently transposed.
